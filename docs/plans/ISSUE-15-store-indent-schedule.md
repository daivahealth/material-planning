# Issue #15 — Store-wise indent schedule

> **Status: implemented** on `feature/store-indent-schedule`. Two deviations
> from this plan, both deliberate:
>
> 1. **Cron resolution is NOT in `settings.DEFAULTS`** (§3.1 said it would be).
>    A store's `settings_priority` can drop the store or hospital level — store
>    157-IP1 in the dev database is configured `item_store,store,hospital` — so
>    the generic walk could resolve a different cron from the one the dispatch
>    loop uses. `indent_schedule.pick_cron` is the single resolver instead.
> 2. **Purchase-request stores are now generated by this run** (generated, not
>    dispatched). The loop previously skipped them entirely, which would have
>    left them with no scheduled generation under the new design.
>
> Validation also enforces "at most one fire per day" by requiring the minute
> and hour fields to be single values — the same rule as §4 option 1, expressed
> in a way the error message can explain.

**Request:** generate indents per store on a configurable schedule — some stores
daily, some on particular days of the week.

**Agreed design:** no new scheduler. The **existing outbound dispatch job** runs
hourly and, on each run, evaluates every store's cron expression to decide which
stores are due. A **mandatory hospital-level cron** is the default; a store-level
cron overrides it. Missed runs are **skipped**, not caught up.

Settled with the maintainer:

| | Decision |
|---|---|
| Tick cadence | **Hourly only** |
| Default cron | **Hospital level, mandatory** |
| Catch-up after downtime | **Skip to the next scheduled time** |
| New scheduler job | **None** — outbound dispatch does the work |
| Archiving old plans | **Later** — not a blocker for this issue |

Nothing blocks the start of this work. One known defect is made worse by daily
scheduling and is **deferred by agreement** (§2); one existing behaviour
constrains sub-daily schedules (§4).

---

## 1. Why this shape is right

Outbound dispatch already does generation **and** dispatch per store, which is
exactly why the separate per-store indent job defaults to off — running both
duplicates the work. Putting the schedule check inside that loop means the
schedule governs the thing that actually runs in production, and nothing new is
introduced.

It also sidesteps everything that has gone wrong with per-store APScheduler jobs
here:

| Per-store jobs | Schedule evaluated in the outbound loop |
|---|---|
| **104 orphaned `indent_store_*` jobs** fired for deleted stores; startup needs explicit pruning | no per-store jobs at all |
| `next_run_time=_now_local()` + `replace_existing=True` **re-anchors the schedule to "now" on every settings save**, and triggers an immediate run as a side effect | schedule is data, read at run time; saving settings changes no timing |
| Every settings save rewrites a persistent jobstore row | jobstore untouched |
| Interval only — no day-of-week, no time | any cron expression |

---

## 2. Deferred: archiving superseded periods

Recorded so it is a known, accepted consequence rather than a surprise.

`indent_duration_days` is the **coverage window** — `period_end = as_of +
indent_days`, default **30**. Today it doubles as the interval, so the two stay
in step by accident. Once the schedule is independent:

> A store generating **daily** with 30-day coverage produces **30 overlapping
> 30-day plans**, and every one persists in `indent_reports`.

Regeneration replaces only the period it generates, so earlier periods remain.
Store 8 already carries 9 periods from occasional runs; daily generation makes
that one new period per day indefinitely.

**Why it is safe to defer.** The damaging symptom — stale quantities on the
Purchase Request screen — is already handled: `/candidates` defaults to the
**newest** period, and the period selector labels older ones *(superseded)*.
Planners therefore see the current plan unless they deliberately pick an old
one. What is left is bookkeeping:

| Residual effect | Severity while deferred |
|---|---|
| `indent_reports` grows ~4,000 rows/day/network | Storage only; no query reads across periods |
| Period dropdown gains one *(superseded)* entry per store per day | Cosmetic, but gets unwieldy within weeks |
| An old period can still be chosen and requested from | Deliberate action, and the label warns |

So this is **follow-up work, not a gate**. Worth scheduling within a few weeks
of daily schedules going live, before the dropdown becomes unusable —
marking or deleting earlier non-PR'd periods on generation, roughly half a day.

## 3. Design

### 3.1 Cron resolution

```
StoreSettings.indent_schedule_cron      -- nullable: NULL = inherit
HospitalSettings.indent_schedule_cron   -- NOT NULL DEFAULT '0 6 * * *'  (mandatory)
```

Adding the key to `settings.DEFAULTS` means `resolve(db, 0, store_id,
"indent_schedule_cron")` already walks store → hospital. Every store therefore
resolves to a cron with **no special case for "unconfigured"** — one evaluation
path, not two.

Making it mandatory at the hospital level is best done as
`ADD COLUMN ... NOT NULL DEFAULT '0 6 * * *'`: it backfills existing rows in the
same statement, enforces the constraint in the database, and stays idempotent
for `start.sh`. Schema-level validation then rejects blanking it.

Defensive case worth handling: a store whose hospital has **no settings row at
all** (`db.get(HospitalSettings, …)` returns `None`). Fall back to the system
default and log a warning rather than skipping the store silently.

### 3.2 Due-detection — window, not catch-up

"Skip to the next scheduled time" makes this simpler than a last-run baseline.
Ask only: **did this store's cron fire inside the hour just elapsed?**

```python
window_start = now - timedelta(hours=1)        # half-open: (window_start, now]
fire = CronTrigger.from_crontab(cron, timezone=_local_tz()) \
                  .get_next_fire_time(window_start, window_start)
is_due = fire is not None and fire <= now
```

Because the window is only one hour wide, fires older than that are never
considered — missed runs are skipped automatically, with no extra logic. Down
from 06:00 to 11:07? The 11:00 run examines `(10:07, 11:07]` only; 07:00–10:00
are gone, as agreed.

**Double-run guard.** Record the fire instant acted upon, not just "when we ran":

```
StoreSettings.last_indent_fire_at TIMESTAMPTZ
```

Skip when the computed `fire` equals `last_indent_fire_at`. This is exact and
holds regardless of tick jitter, a restart mid-run, or a manual dispatch landing
in the same hour as the scheduled one — all of which would otherwise re-generate.

### 3.3 Hourly cadence: the configured minute is not meaningful

With the outbound job on `0 * * * *` and a one-hour window:

| Store cron | Fires | Runs at | Note |
|---|---|---|---|
| `0 6 * * *` | 06:00 | **06:00** | exact |
| `30 6 * * *` | 06:30 | **07:00** | rounded up to the next hour |
| `0 6 * * MON,WED,FRI` | 06:00 Mon/Wed/Fri | **06:00** those days | exact |
| `0 6,18 * * *` | 06:00, 18:00 | 06:00 and 18:00 | but see §4 |

So **only the hour field is effectively honoured**. This must be stated in the
UI, not just the docs, or it will be reported as a bug. The UI should show the
*effective* run time next to what was typed.

### 3.4 Outbound's own cron must be hourly

The schedule check lives inside `run_outbound_dispatch`, so the whole mechanism
is bounded by how often that job runs. The outbound setting's `schedule_cron`
has to become `0 * * * *`; left at `50 14 * * *` (today's value) nothing is
evaluated except once a day at 14:50.

This is a **deployment step, not a code change**, and it is the single easiest
thing to forget. The Outbound Settings screen should warn when `schedule_cron`
fires less than hourly while store schedules exist.

### 3.5 Scheduled versus manual runs

`POST /api/outbound/run` calls the same function. A manual run should dispatch
**everything**, not silently skip stores that are not due — otherwise "Run now"
looks broken.

```python
def run_outbound_dispatch(db, as_of=None, *, respect_schedule: bool = True)
```

Scheduler passes the default; the API endpoint passes `False`. The response
should report `skipped_not_due` so the UI can say *"3 of 200 stores were due"*.

## 4. Constraint: sub-daily schedules dispatch only once per day

Verified in the code, and it limits what a store cron can usefully express.

`dispatch_store` is idempotent on `(store_id, period_start)`, and
`period_start = as_of + 1 day` with `as_of = today`. Two runs on the **same
calendar day** therefore compute the **same** `period_start`, so the second
returns `already_dispatched` and sends nothing.

| Store cron | Generation | Dispatch |
|---|---|---|
| `0 6 * * *` (daily) | ✓ | ✓ |
| `0 6 * * MON,WED,FRI` | ✓ | ✓ |
| `0 6,18 * * *` (twice daily) | runs twice | **dispatches once** — the 18:00 run is a no-op |

Daily and weekly schedules — everything the issue asks for — work correctly.
But a twice-daily cron will silently do nothing the second time.

Three options:
1. **Document and validate** — reject a store cron with more than one fire per
   day, with a clear message. Cheapest, no semantic change. **Recommended.**
2. Include the hour in the dispatch key / request number, so each fire is its
   own document. Larger change to the outbound contract and to consumers.
3. Leave it undefined and let it surprise someone.

## 5. Plan

Starts at Phase 1 — superseding old periods is deferred (§2) and tracked as
separate follow-up work.

### Phase 1 — Data model (0.5 day)
```sql
ALTER TABLE hospital_settings ADD COLUMN IF NOT EXISTS indent_schedule_cron
       VARCHAR(100) NOT NULL DEFAULT '0 6 * * *';
ALTER TABLE store_settings    ADD COLUMN IF NOT EXISTS indent_schedule_cron VARCHAR(100);
ALTER TABLE store_settings    ADD COLUMN IF NOT EXISTS last_indent_fire_at TIMESTAMPTZ;
ALTER TABLE store_settings    ADD COLUMN IF NOT EXISTS last_indent_run_status VARCHAR(20);
ALTER TABLE store_settings    ADD COLUMN IF NOT EXISTS last_indent_error VARCHAR(1000);
```

### Phase 2 — Resolution + validation (0.5 day)
- `DEFAULTS["indent_schedule_cron"] = "0 6 * * *"` (the no-hospital-row fallback).
- Validate on the `*Create` schemas only — the `_IndentDurationRule` precedent, so
  a legacy bad row stays readable and correctable in the UI: 5 fields,
  `CronTrigger.from_crontab` must parse, hospital value may not be blank, and
  (per §4 option 1) at most one fire per day.

### Phase 3 — Schedule check in the outbound loop (1 day)
Resolve each store's cron once per run, evaluate §3.2, skip stores not due, and
record `last_indent_fire_at` / status per store. Add `respect_schedule` (§3.5).
Keep the existing `ItemLevelCache` sharing. Per-store exceptions must not abort
the run — the loop already does this; extend it to record the error.

Return counts: `due`, `dispatched`, `skipped_not_due`, `failed`.

### Phase 4 — API / visibility (0.5 day)
No new endpoints. Add the fields to the settings schemas. Extend the dispatch
response and `GET /api/scheduler/status` so an operator can see, per store: the
resolved cron, whether it came from the store or the hospital, the last fire
acted on, and the next due time.

### Phase 5 — UI (1 day)
- **Hospital settings:** the cron field, required, with validation.
- **Store settings:** optional override; blank shows *"Inheriting from hospital:
  Runs daily at 06:00"*.
- Both: a **human-readable preview** (*"Runs Mon, Wed, Fri at 06:00"*), the
  **next 3 run times**, and the **effective** time when the minute is rounded up
  (§3.3). Presets for Daily / Weekdays / Mon-Wed-Fri.
- **Outbound Settings:** warn when `schedule_cron` is less frequent than hourly
  (§3.4).
- **CSV import:** add `indent_schedule_cron` to `_STORE_SETTING_TYPES`.
  Configuring 200 stores one at a time in the UI will not happen.

### Phase 6 — Tests (1 day)
- Resolution: store overrides hospital; missing hospital row falls back and warns.
- Validation: wrong field count, unparseable, blank at hospital level, more than
  one fire per day.
- Window: `0 6 * * *` is due in the 06:00 run and not in 07:00; `30 6 * * *` is
  due at 07:00 and not 06:00 (pins the round-up).
- Skip, not catch-up: a 5-hour gap runs **once**, for the current hour only.
- Double-run guard: the same fire instant twice in one hour runs once.
- `respect_schedule=False` dispatches a store that is not due.
- Per-store failure does not stop the others; the error is recorded.
- Each seen failing before the fix, per the convention in this repo.

### Phase 7 — Docs (0.5 day)
Functional: the fields, mandatory hospital default, hour-granularity caveat, the
no-catch-up rule, and the one-dispatch-per-day constraint. Technical: resolution,
window evaluation, `respect_schedule`, and the required outbound cron change.

**Estimate: 4.5 days.** Archiving superseded periods (§2) is a separate ~0.5 day
follow-up.

---

## 6. Risks

| Risk | Mitigation |
|---|---|
| Daily generation multiplies stale periods | Accepted (§2). `/candidates` already defaults to the newest period and the selector labels the rest *(superseded)*, so planners see the current plan; archive as follow-up before the dropdown gets unwieldy |
| Outbound cron left at `50 14 * * *` ⇒ schedules never evaluated | Deployment step in the release notes **and** a UI warning (§3.4) |
| Twice-daily cron silently dispatches once | Validate against >1 fire/day (§4) |
| Configured minute appears ignored | Show the effective time in the UI, not just docs |
| "Run now" appears to skip stores | `respect_schedule=False` for the manual endpoint |
| All 200 stores due in the same hour | Sequential, shared `ItemLevelCache`; measured ~19 queries/store, so a few minutes. Stagger hospital defaults if it proves slow |
| Legacy per-store `indent_store_*` jobs still firing | Off by default, so low risk — but the re-anchoring bug should be fixed, or the machinery removed, in a separate change (§7) |

## 7. Left out of scope — flagging deliberately

The existing per-store `indent_store_*` job machinery
(`schedule_store_indent`, `sync_store_indent_job`, `indent_scheduler_enabled`)
is **untouched** by this plan. It defaults to off, so it does no harm today, but
it still carries the re-anchoring bug and the orphan-job problem.

Two options, both outside this issue:
- **Remove it**, now that outbound owns scheduling — simplest end state, but it
  removes the only generation path for a deployment without outbound configured.
- **Keep and fix** — drop `next_run_time=_now_local()` so it stops re-anchoring.

Worth a decision, but not a blocker here.
